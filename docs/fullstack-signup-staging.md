# Full-stack signup staging acceptance

The manual runner in `scripts/vps_signup_acceptance.py` targets only the dedicated VPS QA project on loopback ports 18281–18283. It expects synthetic-only PostgreSQL/Redis/API/web stacks with settings enforcing the QA database names. Run the runtime-isolation verifier before the acceptance runner; never point it at public production origins or reuse production credentials. It creates only synthetic accounts/organizations, performs actual generated-code MFA using the protected staging mail sink, and writes a credential-free result receipt. It does not publish campaigns, grant real-user roles, activate commissions, change prices or record test sessions as actual customer acquisition.

October 27 result: 44 real HTTP checks passed (Individual 11, Institutional 20, OraToPlus 13). The first run identified OraToPlus owner-detail retrieval and a guest-profile assertion mismatch. The defect was fixed while preserving owner isolation; the assertion now verifies absence of account/tenant data in the designed public guest response. Separate real browser checks exercised signup/login/goal routing; separate regressions cover positive and negative saved-result access and QA adapter production rejection.

Staging approval is not launch approval. External inbox delivery, live market/SMDP sources, ASR/TTS/LLM integrations, human institutional qualification and the remaining privacy/finance/commercial gates remain open. All pricing, commission and campaign decisions remain pending founder approval. No production promotion was performed in this run.
